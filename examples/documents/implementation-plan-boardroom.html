Summary

Orders currently reach Atlas ERP in a nightly CSV batch, which oversells stock during campaigns and leaves support reconciling mismatched states by hand. We will replace the batch with an event-driven sync: an order placed in Lumen is visible in Atlas within seconds, with stock held before the customer sees a confirmation. The whole design turns on one number — the reservation must complete inside an 8s SLA, or checkout waits and retries. The work lands in four phases and goes live behind a percentage ramp with the batch running as a shadow until the events prove clean. This plan is waiting on two decisions listed at the end; one of them blocks phase 2.

Scope boundary

In scope. Order creation, stock reservation with an 8-second SLA, payment confirmation via the order.paid webhook, cancellation before shipment.

Out of scope. Returns and refunds (planned separately as Phase 2 of the wider program), product catalog sync, customer master data.

Assumptions. SKUs pre-exist in the Atlas item master; Lumen remains the order ID authority; Atlas staging tenant mirrors production data during testing.

Phases

Phase 1 · no dependencies

Event contract and field mapping agreed

Both teams sign the payload spec for reservation requests and order.paid (field mapping: Lumen order.id → Atlas SalesOrder.ExtId, minor-unit amounts, ISO 4217 currency). The webhook reference document is the source of truth.

Done when
  • Signed payload spec committed to both repos.
  • Sandbox credentials for the Atlas staging tenant issued (currently blocking — decision 2).
Phase 2 · depends on phase 1

Stock reservation flow

Checkout calls Atlas to reserve each line item. Reservation completes within the 8-second SLA; on timeout Lumen shows a "confirming your order" state and retries once with the same idempotency key, which Atlas treats as a status query, never a double hold. Whole-order rejection with per-line reason codes; partial reservations deliberately unsupported.

Done when
  • End-to-end order placed, reserved, and confirmed in staging.
  • Duplicate reservation attempts provably never double-hold stock.
  • Timeout path exercised: second failure behavior per decision 1.
Phase 3 · depends on phase 2

Payment webhook and fulfillment

Payment capture emits order.paid (HMAC-signed, at-least-once, sequence-numbered). Atlas creates the fulfillment order and returns its order number, stored in Lumen as external_ref. Retries back off from 30 seconds to hourly over 24 hours, then park in a dead-letter queue that alerts the integration channel.

Done when
  • Duplicate order.paid deliveries create exactly one fulfillment.
  • Signature verification rejects stale and mismatched deliveries in staging.
  • Dead-letter alerting fires in a forced-failure drill.
Phase 4 · depends on phase 3

Shadow rollout and cutover

Event sync ramps 5% → 50% → 100% of orders while the nightly batch keeps running as a shadow. A reconciliation job compares the two; divergence must be zero before each ramp step. The batch is disabled only after 100% has run clean for 24 hours.

Done when
  • Load test at 3× peak campaign volume holds reservation p95 under 8 seconds.
  • Shadow comparison shows zero divergence at every ramp step.
  • Batch export disabled; reconciliation continues as a nightly guard.

Rollout and rollback

Rollout is the phase 4 ramp itself: percentage-based, shadow-verified, reversible at every step. Rollback is a switch, not a deploy: ORDER_SYNC_MODE=batch re-enables the nightly export and stops event emission. Orders created during event mode keep their external_ref and reconcile normally; the only manual step is releasing stock reservations younger than 30 minutes, for which Atlas ops holds a runbook. Rollback is practiced once in staging before launch day.
