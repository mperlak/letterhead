01Business context

Customers order in the Lumen Commerce storefront; Atlas ERP owns stock, invoicing, and fulfillment. The two systems talk once a day, through a CSV export that runs at night. During campaigns this delay sells stock that is already gone, and every morning someone in support compares order lists by hand to find the states that no longer match.

This specification describes the replacement: an event-driven sync in which an order placed in Lumen is visible in Atlas within seconds, and stock is held before the customer ever sees a confirmation screen. The nightly export disappears; a reconciliation job remains as a guard.

02Scope

Covered. Order creation, stock reservation, payment confirmation, and cancellation before shipment.

Not covered. Returns and refunds (specified separately as Phase 2), product catalog synchronization, customer master data. Each remains on its current process until its own specification is confirmed.

Assumptions. SKUs exist in the Atlas item master before they are sold; Lumen is the authority for order identifiers; the Atlas staging tenant mirrors production data during the test period.

03Flows

Order placement (happy path)

  1. Customer places the order in Lumen Commerce.
  2. Atlas reserves stock for each line item. The reservation must complete within the 8-second SLA.
  3. Lumen sends the confirmation once stock is held; the order shows as confirmed in both systems.
  4. Payment provider captures payment; Lumen emits the order.paid event to Atlas.
  5. Atlas creates the fulfillment order and returns its order number, which Lumen stores as external_ref.

Reservation timeout

  1. Atlas does not answer within 8 seconds.
  2. Lumen shows the customer a "confirming your order" state and retries once, with the same idempotency key.
  3. Atlas treats the repeated key as a status query, never as a second reservation, so a slow first attempt cannot double-hold stock.
  4. If the retry also fails, behavior follows decision 1 in section 06.

Rejected lines

  1. Atlas cannot reserve one or more line items and rejects the whole order, with a reason code per failed line.
  2. Lumen releases the cart and shows the customer which items are out of stock.
  3. Partial reservations are deliberately unsupported: split shipments create invoicing cases Atlas operations asked to avoid.

04Requirements per module

Order module (Lumen)

  • An order that fails reservation is released within one minute, and the customer sees which lines caused it.
  • Every event carries a monotonic sequence number per order; consumers can discard stale deliveries.
  • The checkout "confirming" state resolves to confirmed or released; it never strands the customer.

Stock module (Atlas)

  • A repeated idempotency key returns the current reservation status; it never creates a second hold.
  • Reservations released by rollback expire automatically after 30 minutes; the release runbook covers the manual case.
  • A rejected line's reason code is one the operator can read without a lookup table.

Reconciliation (both)

  • A nightly job compares order states across systems and flags divergence instead of silently correcting it.
  • Divergence above 0.1% of daily orders pages the on-call.

06Open decisions

These are the questions only Atlas can answer; the review round exists for them.

1. Second reservation timeout in a row: hold the order in a pending queue, or fail fast and release the cart?

Blocks the reservation flow and the checkout copy.

2. Who issues sandbox credentials for the Atlas staging tenant, and by when?

Blocks all end-to-end testing.

3. Do cancellations after picking has started require Atlas-side approval?

Does not block: a manual process is acceptable at launch.

4. Should the reconciliation report go to a shared channel or to named recipients on both sides?

Does not block: defaults to the shared integration channel.

5. Is the 30-minute automatic reservation expiry acceptable for campaign periods, or does it need a shorter window?

Blocks the stock module requirements sign-off.
