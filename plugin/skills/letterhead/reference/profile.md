# The brand profile — what the files are and what each one may say

Apply the shared rules in SKILL.md first. `teach` writes these files
(`reference/teach.md` is the procedure); `create`, `polish` and `publish`
only read them.

A profile is what a company looks and sounds like, written down once so
every later document inherits it instead of re-deciding it. It is not a
design system and not a style guide for humans. It is the smallest set of
values a document needs: colors, fonts, logo, voice, and how much certainty
sits behind each one.

## Where a profile lives

- `.letterhead/brand/` — the default brand, used when no name is given.
- `.letterhead/brands/<slug>/` — one profile per named brand, used when the
  user points at it ("for Arkona Supply", "in their brand"). The slug defaults to
  the site's host without the TLD (`https://arkona.example/` → `arkona`).

Five files, same shape in both locations:

| File | Carries | Read by |
|---|---|---|
| `DESIGN.md` | Visual identity: token frontmatter plus one paragraph per section. | This skill and any other tool that speaks the format. |
| `PRODUCT.md` | Voice and audience: who reads this brand's documents, register, vocabulary, anti-references. | This skill and other tools. |
| `tokens.css` | The CSS form of the tokens, in three selector blocks. Generated by `brand-tokens.mjs`, inlined into every document at build time. | This skill, browsers. |
| `profile.meta.json` | The decisions behind the profile: confidence, provenance, questions, and the sentences the sheet needs. | This skill only. |
| `brand-sheet.html` | The one-page sheet published for comments before the first document; its next version lands at the same link. Generated by `brand-sheet.mjs` from the four files above. | Whoever owns the brand. |

A profile without `profile.meta.json` is incomplete. Everything in it then
reads as equally certain, the sheet cannot be generated at all, and a color
scraped off a cookie banner ships with the same authority as one somebody
named.

## `DESIGN.md`

The existing format stays: YAML frontmatter with the design tokens, then
numbered prose sections (Overview, Colors, Typography, Elevation,
Components, Do's and Don'ts). Any file in `styles/` is a worked example of
the same format.

A brand profile's `DESIGN.md` is not a style's. The files in `styles/`
carry a full token set because they are complete on their own; copying that
shape into a profile restates dozens of values nobody decided. A profile's
frontmatter carries the decisions only:

```yaml
---
name: Arkona Supply
description: One sentence: who reads these documents and what the brand looks like.
colors:
  primary: "#ffaf00"
  foreground: "#414042"      # absent when the style's text color is used
  secondary: "#e8b4b8"       # absent unless --accent was passed
  background: "#ffffff"      # absent unless --background was passed
typography:
  body:
    fontFamily: "Roboto, sans-serif"
  heading:
    fontFamily: "Roboto, sans-serif"
    fontWeight: 700
logo:
  on: light                  # the --brand-logo-on the tokens carry
composition:                 # only when composition was measured
  density: regular
---
```

**Keep it short.** One paragraph per section, around forty lines for the
whole file. The frontmatter already carries the values; the prose exists so
a human can argue with the decisions. A `DESIGN.md` that restates every
token in sentences takes minutes to write, nobody reads it, and the
disagreement it was supposed to surface is buried three screens down.

New: a `## 7. Composition` section in prose, and three frontmatter keys.

```yaml
composition:
  density: regular        # compact | regular | airy
  imagery: spot           # none | spot | full-bleed
  rhythm: sectioned       # continuous | sectioned
```

- **density** — how much air the page carries between blocks.
- **imagery** — whether documents in this brand carry pictures at all, one
  or two placed images, or an image that runs the full width.
- **rhythm** — whether sections flow into each other or each one opens with
  a visible break.

Absent keys mean the style governs composition. Do not write a value you
cannot point at a source for: composition comes from a screenshot, a PDF,
or the user's answers, never from the palette. A guessed `airy` outranks a
calibrated style and produces a layout nobody chose.

The prose section says the same thing in sentences a human can argue with,
one short paragraph. When the keys are absent, the section says so and
names what would fill it.

## `PRODUCT.md`

Four things, in the profile's `lang`, each under its own
`##` heading: register, sample, vocabulary, anti-references. The sheet
script matches headings by a word in them, so `## Register`, `## Rejestr`
and `## Odbiorca i rejestr` all count as the register section, and
`## Sample` or `## Przykład` as the sample; the vocabulary heading
(`## Vocabulary`, `## Słownictwo`) and the anti-references heading
(`## Anti-references`, `## Czego unikamy`) are for people, since the sheet
reads the `Unikamy:` / `Avoid:` line wherever it stands. A heading without
one of those words is invisible to the sheet, which then falls back to
`notes`. One paragraph on the register,
one sample paragraph written in it, one line of vocabulary the brand uses
and refuses, one line of anti-references. The sheet takes its tone
paragraph from `notes.tone` first and from the Sample section when that
note is missing. The anti-references
line starts with `Unikamy:` (pl) or `Avoid:` (en) so the sheet can find it;
the same words may also go into `notes.avoid` in the meta file, which the
sheet reads first.

**When nobody has named anti-references,** say that in one sentence ("no
anti-references have been named yet") instead of inventing them. The sheet
still needs its "three words we will not use", and with nothing named those
words are words absent from the text the evidence returned (title, H1,
H2s, sample paragraphs), not a guess about what they dislike; put them in
`notes.avoid`, which the sheet reads before the `Unikamy:` line. Inventing anti-references puts a judgement about a
brand's taste into a file that later tools read as fact.

## What these two files never carry

`DESIGN.md` and `PRODUCT.md` are a shared format. Other tools read them, a
project may already have one, and a human may have edited it.

- No confidence markers. No `(to confirm)`, no `probably`, no
  `confidence: guessed` next to a value. Certainty lives in
  `profile.meta.json`.
- No source notes ("taken from the hero section"). One dated line in the
  file header saying where the profile came from is fine; per-value
  provenance is not.
- No skill-internal references: no command names, no script names, no
  paths inside this skill.

A value written with a hedge beside it gets copied by the next tool without
the hedge, and a guess becomes a fact nobody can trace.

## `tokens.css`

Generated by `scripts/brand-tokens.mjs` from a base style plus the profile's
overrides, never hand-written and never hand-edited. The script fills all
three blocks, computes a text-safe ink variant of the primary when the
primary fails contrast on paper, embeds the logo, and exits non-zero on a
contrast failure it cannot fix. Hand edits are how a file ends up with a
tuned `:root` and dark blocks copied from somewhere else. The state colors
(`--status-ok`, `-warn`, `-blocked`, `-neutral`) come from the base style
and are kept where they read at 4.5:1 on the brand's paper, walked darker or
lighter where they do not; a profile taught before they existed gets them
from `apply-tokens.mjs` at build time, worked out the same way.

The three-block contract stays: `:root`, `[data-theme="dark"]`, and the
`@media (prefers-color-scheme: dark)` fallback scoped to
`:root:not([data-theme="light"]):not([data-theme="dark"])`. All three carry
the full color surface. A file with only `:root` filled gives dark-mode
readers black text on a black page.

The brand's fonts sit at the top of the file, before the three blocks,
as `@font-face` rules with the font files inlined as `data:` URIs, between
`/* letterhead:fonts */` and `/* /letterhead:fonts */`. They come from
`--embed-fonts` (Google Fonts, or a licensed file the owner supplied), and a
regenerated file replaces the whole section. A document that inlines
`tokens.css` carries its fonts with it; one that loads them from a font
service shows fallback type in every review frame, where the network is
closed.

The logo tokens:

```css
:root {
  --brand-logo-mask: url("data:image/svg+xml;base64,PHN2ZyB4bWxucz0i…"); /* single-color artwork */
  --brand-logo: var(--brand-logo-mask);   /* the image, in the light theme's color */
  --brand-logo-color: oklch(0.373 0.004 308.4);
  --brand-logo-on: light;                 /* dark | light */
  --brand-logo-ratio: 3.6;                /* width / height of the artwork */
}
[data-theme="dark"] {
  --brand-logo-color: oklch(0.925 0.007 248);
  --brand-logo-on: dark;
}
```

- **`--brand-logo`** is a data URI, never a remote URL, because documents
  are self-contained and a hotlinked logo breaks the day the brand
  redesigns its site. SVG first, then PNG, then JPG. Hard limit 200 KB
  after encoding. Over the limit, or no usable logo at all: leave the token
  out and let documents set a text mark from the company name. An 800 KB
  logo makes every document a multi-megabyte attachment that mail clients
  refuse. For single-color artwork the data URI sits in
  `--brand-logo-mask` and `--brand-logo` points at it, so there is one copy
  either way. An SVG wordmark set as `<text>` carries its font inside the
  data URI, counted against the same limit; an image cannot reach the
  document's fonts.
- **`--brand-logo-on`** names the background the logo is legible on, not
  the background of the page. `dark` means the artwork is light-colored and
  needs something dark behind it.
- **`--brand-logo-ratio`** is the artwork's width over its height, read
  from the file. Documents size the logo box with it
  (`width: calc(40px * var(--brand-logo-ratio))`) instead of decoding the
  image, so a wordmark is never squeezed into a box of the wrong shape.

**White artwork on transparency** is the common case behind dark site
headers, and the evidence script flags it as `whiteOnTransparent`. It is
legible on nothing that a light document provides. Handling, in order:

1. **Single-color artwork** (almost every white logo): pass
   `--logo-tint <colors.foreground>` to `brand-tokens.mjs` (hex or
   `oklch()`). The script recolors it to the text color, keeping the shape
   and the anti-aliased edges, and sets `--brand-logo-on: light`. The logo
   sits on paper like any dark logo. No question on the sheet;
   `notes.logo` says it was recolored.
2. **Multi-color artwork** (the script refuses to tint it): set
   `--brand-logo-on: dark` (pass `--logo-on dark`) and have documents lay
   the logo on a solid dark header band, `var(--brand-logo-plate)`, which
   the script sets to the brand's dark text color. The sheet then asks for
   the opposite variant.

Dropping white artwork straight onto paper produces a document whose header
looks empty, which every reader reads as a broken file.

**Dark mode** is handled by `brand-tokens.mjs`, in one of three ways:

- **Single-color artwork on paper** (a tinted logo, or any one-color mark):
  one copy in `--brand-logo-mask`, drawn as a mask filled with
  `--brand-logo-color`. `:root` sets that color to the tint (or the
  artwork's own color when it reads on paper, or the text color); both dark
  blocks set it to the dark theme's text color. The logo turns light in
  dark mode with no second copy and nothing behind it. Documents that still
  draw `var(--brand-logo)` as a background get the light-theme image.
- **Multi-color artwork on paper:** one mask color would flatten it, so
  both dark blocks carry `--brand-logo-dark`, a copy recolored color by
  color (colors with 3:1 on the dark page stay, near-neutral ink becomes
  the dark text color, a too-dark brand color is lifted at its hue), and
  point `--brand-logo` at it. Documents draw `var(--brand-logo)` and get the
  right artwork in each theme. A light plate on a dark page looks pasted
  on, so it is only the fallback for artwork the script cannot read color
  by color (gradients, JPGs): the dark blocks then set `--brand-logo-plate`
  to a light color and `:root` sets it to `transparent`.
- **Artwork on a dark band** (`--brand-logo-on: dark`): `--brand-logo-plate`
  is the same dark color in all three blocks, so the band stays dark in
  both themes instead of turning into the dark theme's light text color.

The dark theme keeps the brand color itself as `--primary` whenever it has
3:1 on the dark page, and lifts its lightness only as far as 3:1 when it
does not, with the same hue and as much chroma as the screen can show.
`--muted`, `--border` and `--muted-foreground` take the brand's hue at a
very low chroma, so a red brand does not sit on the style's bluish greys.

## `profile.meta.json`

The decision record for the profile, and the only file the two scripts read
for anything the agent chose. Internal to this skill.

```json
{
  "schema": 1,
  "brand": "arkona",
  "lang": "pl",
  "style": "corporate",
  "collectedAt": "2026-09-17T07:10:00Z",
  "sources": [
    { "id": "url1", "type": "url", "ref": "https://arkona.example/", "fetchedAt": "2026-09-17T07:09:12Z" },
    { "id": "int1", "type": "interview", "ref": "user, 2026-09-17" }
  ],
  "fields": {
    "name":                    { "value": "Arkona Supply", "confidence": "inferred", "sources": ["url1"], "note": "Z metadanych strony i ze stopki." },
    "colors.primary":          { "value": "#ffaf00", "confidence": "inferred", "sources": ["url1"], "note": "Najczęstszy kolor strony, na przyciskach i w nawigacji." },
    "colors.foreground":       { "value": "#414042", "confidence": "inferred", "sources": ["url1"], "note": "Kolor tekstu strony, ciemnoszary, nie czarny." },
    "typography.body":         { "value": "Roboto",  "confidence": "inferred", "sources": ["url1"], "note": "Krój tekstu strony, dostępny w Google Fonts." },
    "typography.heading":      { "value": "Roboto",  "confidence": "inferred", "sources": ["url1"], "note": "Nagłówki używają kroju tekstu." },
    "typography.headingWeight":{ "value": 700,       "confidence": "inferred", "sources": ["url1"], "note": "Nagłówki na stronie są pogrubione (700)." },
    "logo":                    { "value": "themes/arkona/images/arkona-logo.png", "confidence": "inferred", "sources": ["url1"], "note": "Białe logo z nagłówka, przebarwione na kolor tekstu." },
    "voice.register":          { "value": "rzeczowy ton B2B", "confidence": "inferred", "sources": ["url1"] },
    "voice.sample":            { "value": "Dostarczamy komponenty na czas i mówimy wprost, kiedy termin jest zagrożony.", "confidence": "inferred", "sources": ["url1"] }
  },
  "questions": [
    { "id": "q-name-form", "field": "name", "text": "Której formy nazwy używają Państwo w dokumentach?", "why": "Trafia do nagłówka każdego dokumentu." }
  ],
  "notes": {
    "name": "Nazwa z alt logo i stopki.",
    "logo": "Logo ze strony jest białe; przebarwiliśmy je na kolor tekstu, żeby stało na jasnej kartce.",
    "tone": "Piszemy krótko, konkretnie, bez marketingowego zapału."
  }
}
```

**Top-level keys.**

| Key | Meaning |
|---|---|
| `schema` | Format version. `1` today. |
| `brand` | Profile slug, or `"brand"` for the default brand. |
| `lang` | `"pl"` or `"en"`: the language of the sheet and of all prose in the profile: `notes`, `questions`, each field's `note`, and `PRODUCT.md`. The sheet's headings and labels follow it; the section ids do not. The sheet mixes whatever language the prose is in with its own labels, so an English note on a Polish sheet reads as a slip; `brand-sheet.mjs` warns when a sentence looks like the other language. |
| `style` | Base style slug (`corporate`, `consulting`, …). What `brand-tokens.mjs` starts from and what supplies composition. |
| `collectedAt` | When the evidence round ran, ISO 8601 UTC. |
| `sources[]` | `{ id, type, ref, fetchedAt }`. `type` is one of `url`, `pdf`, `document`, `screenshot`, `interview`, `owner`. `ref` is the URL, the file path, or who was asked and when. `fetchedAt` is optional for `interview` and `owner`. |
| `fields{}` | The decisions. Fixed key list below. |
| `questions[]` | `{ id, field, text, why }`, agent-authored, at most five, ids of the form `q-<slug>`. `text` is the question in the sheet's language, `why` is one line on what the answer changes. The sheet renders each one as its own `h3` with `id` = `id`. |
| `notes{}` | `{ name, logo, tone, preview?, avoid? }`: the three sentences the agent writes for the sheet, in the sheet's language, plus `preview` only next to a real `preview{}`, and an optional `avoid` array (the words the sheet lists as "we will not use"). Plain language only: no field names, metadata keys, or CSS tokens in these sentences. In Polish, address the brand owner formally everywhere (`Państwo`, `Państwa`, `mają Państwo`), in `notes` and `questions` alike: the sheet's fixed labels already use that form, and one informal sentence next to them reads as a slip. Everything else on the sheet is generated from the profile. |
| `preview{}` | Optional, and absent by default. Without it the sheet shows a sample document about the profile itself, laid out by the base style: what was read and how sure each field is, the colors with swatches, the open questions and the next steps, with a visible "sample" label. Write `{ title, nextStep }` only when the user gave a real document or topic: its real title and real next step. A made-up project on the sheet gets read as a real one, and the owner's first comment is "what project is this?". |

**Fields.** `fields{}` carries decision-bearing values only, not every token.
Exactly these keys, and no others:

`name`, `colors.primary`, `colors.foreground`, `typography.body`,
`typography.heading`, `typography.headingWeight`, `logo`, `voice.register`,
`voice.sample`, plus `colors.secondary` when the brand names its own accent,
and `composition.density`, `composition.imagery` and `composition.rhythm`
when composition was actually measured.

`logo` is one key covering both logo tokens, artwork and
`--brand-logo-on`. Keys are dot paths mirroring where the value landed, so
the sheet and a question can both say which field they mean; invented keys
break that link.

| Key | Meaning |
|---|---|
| `fields.<key>.value` | The decision. `null` when the field was deliberately left open. |
| `fields.<key>.confidence` | `confirmed` \| `inferred` \| `guessed`. |
| `fields.<key>.sources` | Ids from `sources[]`. Empty array when nothing supports the field. |
| `fields.<key>.note` | One short sentence of evidence. This is what the sheet turns into "where this comes from". |

Everything else a document needs — surfaces, borders, tints, spacing, and
the accent when `colors.secondary` is absent — is derived by
`brand-tokens.mjs` from the style and these values. Listing derived tokens
here makes the file long, makes the sheet look like a design system, and
invites questions about values nobody chose.

**Where each field goes.** Every field that shapes the tokens reaches
`brand-tokens.mjs` as one flag. A field with no flag in this table does not
change `tokens.css`, so a value written into the profile but not passed
shows on the sheet and never in a document.

| Field | `brand-tokens.mjs` flag | Tokens it sets |
|---|---|---|
| `colors.primary` | `--primary` | `--primary`, `--primary-ink`, `--ring`, `--chart-1` |
| `colors.foreground` | `--foreground` | `--foreground`, card and popover text |
| `colors.secondary` | `--accent` | `--accent` (as given in `:root`, a dark fill of its hue in the dark blocks), `--accent-foreground`, `--accent-surface` and its foreground (the accent as a large fill: a light tint of a strong accent's hue) |
| `DESIGN.md` `colors.background` | `--background` | `--background` |
| `typography.body` | `--font-body` | `--font-sans` |
| `typography.heading` | `--font-heading` | `--font-display` |
| `typography.headingWeight` | `--heading-weight` | `--font-heading-weight` |
| `logo` | `--logo` (plus `--logo-on`, `--logo-tint`) | `--brand-logo*` |

`name`, `voice.*` and `composition.*` are read by the sheet and by
`create`, not by the tokens script.

**Confidence.**

- `confirmed` — the owner said so, in a comment on the sheet or in
  writing. Nothing the agent worked out is ever `confirmed`, however
  obvious the evidence looked. The whole point of publishing the sheet
  first is that the value comes from the person who owns the brand.
- `inferred` — the evidence is unambiguous: a saturated non-vendor color on
  buttons and navigation, a font named in the `body` rule, a header logo
  with sane proportions.
- `guessed` — the evidence is thin or contradictory, or the value is a
  default we picked to have something.

Confidence labels a value on the sheet. It does not decide what gets asked:
`reference/teach.md` § 3 does, and a `guessed` tint is still not a question.

**Rules.**

1. An entry per decision, not per token. The nine keys above (plus
   `colors.secondary` when the brand names an accent, and composition when
   it was measured) are the whole list. A value with no
   entry is a value nobody can question later; an entry for a derived token
   is noise that makes the real decisions harder to find.
2. Fields left deliberately open get an entry with `value: null`, so the
   agent can see what is missing instead of silently skipping it.
3. Refresh mode changes only the fields the round actually touched. It
   rewrites their `value`, `confidence`, `sources` and `note`, and leaves
   every other entry byte-identical. A refresh that regenerates the whole
   file reverts corrections made last round, and nobody notices until the
   wrong color ships again.
4. A field somebody corrects becomes `confidence: "confirmed"` with an
   `owner` source naming the round it came from.

## Precedence: brand against style

SKILL.md § Brand precedence decides which profile applies. These five rules
decide, field by field, what happens when a profile and a style both have
an opinion.

1. **The style supplies everything the profile does not.** Colors, fonts,
   composition, register, signature moves. A style is complete on its own.
   Without this rule a thin profile produces a document made of bare tokens
   and default margins, which reads as unfinished work.
2. **The profile overrides the style's colors (in both themes), fonts,
   voice and logo; the style keeps its layout.** Named values in a profile
   are binding. Without this rule a style
   repaints a confirmed primary color, and the reader receives a document in
   somebody else's blue.
3. **A filled `composition` block overrides the style's composition; an
   empty one leaves composition to the style.** Without this rule a density
   guessed from one screenshot outranks a calibrated style, and documents
   drift airy or cramped for no reason anyone recorded.
4. **A one-off override from the user wins over both, and gets recorded.**
   "Ignore the brand" or "in the engineering style anyway" applies to that
   document only, is stated in the shape gate, and goes into the file as an
   HTML comment. "In the engineering style anyway" keeps the brand and
   changes the layout: `apply-tokens.mjs <profile> <file> --style
   engineering`. Without the record, the next person to open the document
   reads a deliberate choice as a mistake and re-brands it.
5. **No profile means a style the user confirmed, never an invented
   palette.** Propose a style by recipient and wait for the answer. Without
   this rule a palette derived from the topic ships looking like a decision
   somebody made, and the reader assumes those are their colors.

Precedence resolves per field, not per file. A profile that names only a
primary color and a body font takes those two and leaves the rest to the
style; it does not drag the whole style into "no opinion".

## Failure modes

**Confidence leaking into the shared files.** `primary: "#ffaf00" # to
confirm` in `DESIGN.md`. The next tool reads the value and drops the
comment, and a guess becomes a documented brand color.

**A profile with no meta file.** Written by hand, or by a run that skipped
the sidecar. `brand-sheet.mjs` has no notes and no questions to
render, so there is no sheet at all, and whatever gets sent instead asks
nobody to correct anything.

**`confirmed` awarded by the agent.** The evidence was strong and the value
is almost certainly right, so the field ships as agreed without anybody
agreeing. Strong evidence is `inferred`. Confirmation comes from a person.

**A meta file of tokens.** Twenty entries covering surfaces, borders and
tints. The decisions are in there somewhere, the file takes minutes to
write, and the sheet built from it reads as a design system nobody asked
for.

**Full-file refresh.** Two fields came back corrected; the refresh
regenerated all of them from the original evidence and quietly undid the
correction. Refresh is a diff over `fields{}`, same as `polish` is a diff
over a document.

**A logo that is not there.** `--brand-logo` pointing at a remote URL, or a
600 KB PNG inlined, or white artwork with no `--brand-logo-on`. All three
produce documents with a broken or invisible header; the text mark is
better than any of them.

**Tokens that only work in one theme.** `:root` carefully tuned by hand, the
two dark blocks copied from the reference style. The brand survives in light
mode and dissolves in dark. This is what `brand-tokens.mjs` exists to stop;
an agent editing `tokens.css` reintroduces it.
